2. The problem and the approach

The problem

The ML side of TriageLens trains a model to flag possible TB on chest X-rays. Before any training, you need data whose labels you trust, split in a way that gives an honest score. The Shenzhen set from the US National Library of Medicine has 662 PNG X-rays. The label is in the file name (CHNCXR_0001_0.png: 0 means normal, 1 means abnormal lung). Each image also has a short text reading with sex, age and the finding.

If you feed this straight into training, several things can go wrong without anyone noticing:

  • Some labels do not mean what you need. Label 1 means "abnormal lung," not "TB."
  • Some patients are children, who are outside the intended use (TRD 9.1).
  • Copies of the same image can end up in both training and test, so the test score is too high.
  • The dataset can change between runs, so two results that look comparable are not.

The approach: a pipeline of checks

The pipeline runs stages in a fixed order. Each stage removes the records that fail its checks and writes them to a quarantine file with a reason.

  1. Ingest. File name schema, image decodes, smallest side at least 512 px, reading present for at least 95% of images.Bad record: quarantine. Fewer than 95% of readings present: hard fail.
  2. Label. The file label must agree with the written reading.Disagreement or doubt: quarantine for human review.
  3. Dedup. Copies with different labels, exact copies, then near-identical images and shared patient IDs are grouped.Clashing or exact copies: quarantine. Near copies: kept, but grouped together.
  4. Policy. Age 15 or over, age readable.Fails: quarantine.
  5. Split. Whole groups go to train, validation or test, keeping v1's split where one exists.
  6. Batch checks. No leakage across splits, balanced TB rate, enough records.Any failure: hard fail. No manifest is written.
  7. Outputs. Committed: manifest, quarantine list, near-duplicate pairs, run report. Private (git-ignored): sex, age and reading text.

Two kinds of failure

The design separates two kinds of problem. A quarantine handles one bad record: it is set aside with a reason, and the run goes on. A hard fail handles a problem with the whole dataset: if 10% of readings are missing, or one split has the wrong TB rate, no single record is to blame and the output cannot be trusted. So the run stops and writes nothing. The rule "no record is dropped silently" means every removed record is listed in quarantine.csv.

  • 47-48A custom exception type. Raising it anywhere unwinds the whole run. main() catches it, prints HARD FAIL, and returns exit code 1.
  • 274-276q() adds one row to the quarantine list: file, patient ID, label, the stage, the check name and a reason. Each stage calls it and then filters the record out of the DataFrame.
  • 385Batch checks run only after every record-level stage is done, on the final split.
  • 387-389If any check failed, the pipeline writes only batch_checks_failed.json (so you can see why) and raises HardFail before any manifest is written.

3. Core concepts

Ten concepts, roughly in the order the pipeline uses them. Splitting comes first because it is the reason most of the other checks exist.

3.1 Data leakage and patient-level splits

The idea

A model is scored on data it did not learn from. So the data is cut into splits: a training set to learn from, a validation set for tuning and choosing thresholds, and a held-out set used rarely, for the final score. The score means something only if nothing from the held-out set reached training.

Data leakage is when it does. With X-rays, the usual cause is the same person appearing in two splits. Two X-rays of one person share things that have nothing to do with TB: body shape, rib pattern, implants, how the person stood. A model can learn to recognise the person, then "recognise" them again in the test set. The test score goes up, but the model has not got better at spotting TB. In a clinic, that model would do worse than its score promised.

General background

Patient-level splitting is standard practice in medical imaging ML for exactly this reason. The project makes it a rule: "Splits are made by patient, never by image" (TRD ML-DATA-02).

The rule

Assign splits to groups of records (one patient, plus any near-identical images), never to single images. Afterwards, check that every patient ID and every group sits in exactly one split.

How often does an image-level split leak? Say each image is put in train, validation or test at random with chances 0.70, 0.15 and 0.15. A patient with k images stays leak-free only if all k land in the same split:

P(leak | k images) = 1 − (0.70k + 0.15k + 0.15k)

For k = 2: 1 − (0.49 + 0.0225 + 0.0225) = 0.465. Nearly half of all two-image patients would leak. For k = 3 it is 0.650. (General probability, assuming each image is assigned independently.)

Worked example

In v2, the 618 kept records form 618 groups, split 431 / 94 / 93. The batch check counts, for each patient_id, how many distinct splits it appears in. The maximum is 1, so no_patient_across_splits passed.

Note: in Shenzhen, the "patient ID" is the provider's image sequence number (data card), and every kept record is its own group. So on this dataset the grouping does not merge anything. The code is still built for data where one person has several images. See section 4.

3.2 Stratification and prevalence

The idea

Prevalence is the share of records that have the condition. Here, that is the TB rate. A purely random split of a small dataset can, by chance, give a validation set with noticeably fewer TB cases than the rest. Then the thresholds you tune on it, and the scores you report, describe a different mix of patients.

Stratified sampling fixes this. Split each label separately with the same fractions, then combine. Each split then mirrors the overall TB rate almost exactly.

The rule

For each label ℓ with nℓ groups:

n_train = round(0.70 × n)
n_val   = round(0.15 × n)
n_test  = n − n_train − n_val

Then check each split s against the overall rate p:

| p_s − p | ≤ 0.05

Which groups land where comes from a shuffle driven by a fixed seed (591). The same input always gives the same split.

Worked example

The code

Line by line

  • 203One random generator, seeded once. Every shuffle below draws from it in turn.
  • 205Sort by group_id first, so the order of the input rows cannot change the result. Then groupby("label") handles label 0, then label 1. This is the stratification: each label is split on its own.
  • 206-207Copy the group IDs for this label and shuffle them in place.
  • 208-210The formula: train and validation sizes by rounding. Python's round rounds an exact half to the even number.
  • 211-216Slice the shuffled list: first n_train to train, the next n_val to validation, the rest to test. The test split takes whatever rounding left over, so the counts always add up to n.
  • 259Overall TB rate. The mean of 0/1 labels is the share of 1s.
  • 260-263One check per split: the gap must be at most 0.05.

One detail matters later: the generator is shared. Label 1's shuffle starts from wherever label 0's shuffle left the generator. Label 0 goes first, so changing the number of TB groups does not change the normal records' splits. Changing the number of normal groups changes both.

3.3 Keeping splits across versions

Gap

You said this was suggested and you accepted it. The data card records that the team agreed it on 21 Oct 2026. Here is why it matters.

The idea

Datasets get new versions. v2 added stricter label checks, which removed 17 records. The obvious thing to do is re-run the split on the new, smaller list. But a shuffle of a different-length list gives a different order, so many records would land in a different split.

Now picture a model trained on v1 and scored on v2's test split. Some of v2's test images were v1 training images. Each version is leak-free on its own, but taken together they leak. That is leakage across versions.

The fix: every group keeps the split it had before. Removing records then only shrinks splits; nothing moves. Only groups that are completely new get a fresh split.

The rule

For each group G, collect the prior splits of its files that appear in the old manifest:

S = { prior_split(f) : f ∈ G, f in old manifest }
|S| = 1 → keep that split
|S| = 0 → new group: split with assign_splits
|S| > 1 → hard fail

Worked example

removed by stricter rule (all TB)−13−1−3−17
v24319493618

The v2 report shows "carried": 618, "new": 0. No record changed split.

What re-splitting would have done, measured on the synthetic set on 10 Nov 2026: one TB reading was made ambiguous, so that record was quarantined, and the set was split fresh. 92 of the 199 remaining TB records changed split, 21 of them from train to test and 24 from test to train. No normal record moved, because label 0 is shuffled first (see 3.2).

The code

Line by line

  • 229-230Read the old manifest and build a map from file name to split. File names hold the patient number and label, so they are stable keys.
  • 232Go through the new groups, one at a time.
  • 233The set S: the old splits of this group's files, skipping files that are new.
  • 234-235|S| > 1: the group's files were in two splits before. Either v1 leaked, or new grouping links records that v1 kept apart. Any choice would move a record, so the run stops.
  • 236-237|S| = 1: keep that split.
  • 238-239|S| = 0: remember the group as new.
  • 240-242Split only the new groups, with the same stratified, seeded assign_splits.
  • 243Return the splits and the counts. Both counts are numbers of groups, not records.

3.4 Record checks and intended population

The idea

Intended use says who a tool is for. For TriageLens chest X-rays, that means people aged 15 and over (TRD 9.1, 3.2). Training data from outside that group teaches the model about patients it will never be used on, and validation scores then describe the wrong population. So the pipeline removes records under 15. It also removes records whose age it cannot read, because it cannot confirm they belong.

That second rule takes the cautious side. When the code is unsure, it excludes the record instead of guessing. The project's result screens follow the same spirit ("uncertainty moves toward refer or retake").

To read ages, the code has to parse messy free text. The real readings include femal (a typo), male45yrs (no space), 61yr (singular) and stray tabs. A regular expression that is too strict would quarantine good records. One that is too loose would read the wrong number.

Gap: the 512 px floor

You accepted this. The only reason in the files is the code comment on line 36: the model input is 320 px (TRD 10.6), and 512 "leaves room to crop to the lungs before resizing." On real data this check never fired. The smallest side of any kept Shenzhen image is 2009 px (v2 report).

The rule

sex = first match of (female | femal | male) in the header
age = number followed by yr / yrs / year / years / y
     or 0 if the number is followed by months / days
     or unknown otherwise
keep only if age is known and age ≥ 15

Worked example

Raw reading: male45yrs  \t\r\nnormal

  1. Remove \r, split on newlines, strip each line, drop empty ones: ["male45yrs", "normal"].
  2. Header, lower-cased: male45yrs. The sex pattern matches male. There is no word boundary between e and 4, which is why the pattern does not use \b.
  3. The age pattern matches 45yrs: age 45.
  4. Finding: normal.

In v2 this stage quarantined 25 records under 15 and 1 whose reading gave a number with no unit.

3.5 Label noise and a conservative gate

The idea

Label noise means some training labels are wrong. In Shenzhen there is a specific trap: label 1 means "abnormal lung," not "TB" (data card). A TB model trained on those labels would partly learn "anything abnormal," pneumonia included. So the pipeline uses the written reading to confirm each label before keeping the record.

Think of the label check as a filter that decides "is this a confirmed TB record?" Like any filter, it trades two kinds of error:

  • Precision: of the records it keeps as TB, how many really are TB.
  • Recall: of the real TB records, how many it keeps.

A conservative gate puts precision first. Anything doubtful goes to a person for review, even if that loses some true TB records. Losing a good record costs a little data. Keeping a wrong label teaches the model something false, and you cannot see the damage later.

Gap: why conservative

You did not know. The files give this reason: the word list is "a validation gate, not a clinical text classifier." Negation, uncertainty or mixed findings "require a human decision" (docstring, lines 113 to 121). No one on the team can read clinical text as a radiologist would, so the code does not try. It sends doubt to review.

The rule

label 0: keep only if the whole finding is a plain "normal"
label 1: review if it contains any doubt word or "?"
         else keep only if it names TB as a whole word

Three regex ideas make this work:

  • Word boundary \b: the point between a word character (letter, digit, underscore) and a non-word character, or the start or end of the text. The TB pattern is \bp?tb\b: an optional "p", then "tb", as a whole word. It matches "tb" and "ptb" but not "stb" or "atb".
  • Full match: the pattern must cover the whole string. "normal; right pneumonia" fails for label 0 even though it starts with "normal".
  • A doubt word list: "no", "not", "possible", "suspect...", "rule out", "?", and also "normal" itself, since "normal" in a TB reading means a mixed finding.

Worked example

bilateral PTB, label 1: no doubt word. \bp?tb\b matches "ptb". Kept.

right STB, NATB, label 1: no doubt word. In "stb", the letters "tb" follow "s". Both are word characters, so there is no boundary before "t", and p? cannot take an "s". No match. Quarantined: "label 1: reading does not name TB."

That second case is real. In v2, 18 TB-labelled records were quarantined: 16 use STB (probably secondary TB, not confirmed), 1 has a question mark, and 1 reads pneumonia. If the 16 STB readings are TB, the gate kept 316 of 332 probable TB records, a recall of about 95%. That figure is derived from the data card counts and assumes STB means TB.

Documented history

The STB gap was found in the PR #78 review, once pipeline 0.2.1 wrote the matched word into each quarantine reason. Fixing it changes the dataset, so it waits for v3 (pipeline README, data card).

3.6 Cryptographic hashing: exact copies, cache keys, version hash

The idea

A hash function turns input of any length into a fixed-size number, the digest. A cryptographic hash such as SHA-256 adds strong guarantees:

  • The same bytes always give the same 256-bit digest.
  • Changing even one bit of input flips about half of the output bits. This is the avalanche effect.
  • Finding two different inputs with the same digest (a collision) is not possible in practice.
General background

These properties are standard for SHA-256. Together they make the digest work as a fingerprint of the exact bytes.

The pipeline uses that fingerprint three ways:

  1. Exact duplicates. Two files with the same SHA-256 are the same bytes. Keep the first and quarantine the rest.
  2. Cache keys. Decoding about 660 large X-rays takes minutes, so results are cached. The cache key includes the SHA-256 of the file's current bytes. A key built from file size and modified time can stay the same while the bytes change. A content key cannot. The key also includes the hash size and the Pillow version, because decoding and resizing depend on the code too.
  3. Dataset version hash. One fingerprint for the whole dataset. Change any file, any byte or any split, and it changes. The label is part of the file name, so a label change changes it too.

What SHA-256 cannot do: an image saved again with different PNG compression has the same pixels but different bytes, so its SHA-256 differs completely. Catching that needs the perceptual hash in 3.7.

The rule

version = first 16 hex characters of
  SHA-256( join("\n", file + ":" + sha256 + ":" + split) )
over the kept records, sorted by file name

16 hex characters are 64 bits. That is far more than enough to tell versions apart.

Worked example

  • v1: 702a4658c7447e13. v2: 0445b087fed038c4. They differ because 17 records were removed.
  • Pipeline 0.2.0 and 0.2.1 gave the same v2 hash. Only the quarantine reasons and the report changed. The records, bytes and splits did not (data card).
  • The synthetic set's clean run gave 1dd066baf6b0a52f in the README. A re-run on 10 Nov 2026 on this machine gave the same hash.

3.7 Perceptual hashing and Hamming distance

The idea

A perceptual hash is a fingerprint of what an image looks like, so images that look alike get hashes that are alike. It is the opposite of SHA-256, where nearby inputs give unrelated outputs.

The difference hash (dHash) works like this:

  1. Convert to grayscale and shrink the image to 17 × 16 pixels using Lanczos resampling.
  2. In each row, compare each pixel with its right-hand neighbour. Write 1 if the neighbour is brighter, 0 if not. 16 rows × 16 comparisons = 256 bits.

The bits record the direction of brightness changes, not the brightness itself. So the hash survives resizing (it shrinks everything anyway), recompression and an even brightness shift (both neighbours change by the same amount).

To compare two hashes, count the bits that differ. That count is the Hamming distance. 0 means identical hashes. For two unrelated random 256-bit strings, the expected distance is 128.

General background

The 128 comes from basic probability: each bit differs with chance one half, so 256 bits give a binomial with mean 128 and standard deviation 8.

The rule

bit(r, c) = 1 if g[r][c+1] > g[r][c] else 0,  r = 0..15, c = 0..15
d(a, b) = popcount(a XOR b)
near-duplicate if d ≤ 12

The threshold has to sit above the distances that real copies produce (a resized copy) and below the closest pair of truly different X-rays. It was chosen from the data.

Worked example

By hand, one row of five pixels: [10, 30, 30, 20, 50]

  • 30 > 10 → 1
  • 30 > 30 → 0 (equal is not brighter)
  • 20 > 30 → 0
  • 50 > 20 → 1

Row bits: 1001.

On real data, the committed dHashes of CHNCXR_0001_0 and CHNCXR_0002_0 differ in 54 bits (computed from the v1 manifest on 10 Nov 2026). Across all 201,295 pairs of v1's 635 images, the closest pair is 21 bits apart and the median is 72. The README gives a median of 73, probably measured over a slightly different set of images. No pair is within 12 bits, so the threshold sits well below every real pair. A median of 72, far below 128, shows that chest X-rays look much more alike than random images do.

Documented history

The first version used a 64-bit (8 × 8) dHash with a threshold of 4 bits. At 8 × 8, chest X-rays all look alike: two lungs, a spine and ribs in the same places. Small distances linked 416 of 662 X-rays into one group (see chaining in 3.8). That giant group went into one split, the TB-rate batch check failed, and the run stopped. The fix was the 256-bit hash (pipeline README).

The code

Line by line

  • 39-40A 16 × 16 grid, so 256 bits, and the threshold of 12.
  • 63Grayscale ("L"), then resize to width 17 and height 16. Seventeen columns give 16 neighbour pairs per row.
  • 64Turn the image into a numpy array of integers.
  • 65a[:, 1:] is every column except the first, a[:, :-1] every column except the last. Comparing them checks every pixel against its right-hand neighbour in one step. That is the formula. flatten() reads the 16 × 16 result row by row.
  • 66Join the bits into a binary string and read it as one 256-bit Python integer.
  • 70XOR leaves a 1 wherever the bits differ. Counting the 1s gives the Hamming distance.
  • 147-153Where the distance is used against labels: any two records within 12 bits whose labels differ are both flagged. Exact copies have distance 0, so they are covered too. This runs before duplicates are merged, so keeping "the first copy" can never hide a clash.

SHA-256 catches only byte-identical files. dHash also catches the same picture with different bytes: resized, recompressed, slightly brighter. 3.8 Union-find and transitive chaining

The idea

The pipeline has a list of links: "these two records share a patient ID" and "these two images are within 12 bits." It needs groups such that any two linked records share a group. In graph terms, records are nodes, links are edges, and the groups are the connected components.

Grouping is transitive. If A links to B and B links to C, then A, B and C form one group, even when A and C look nothing alike. That is correct for leakage, since A must not be in train while C is in test if B connects them. But it is also a risk. With a loose threshold, links chain across the dataset and form one giant group. That is what happened with the 64-bit hash.

Union-find (also called a disjoint-set structure) builds these groups efficiently. Each record points to a parent. A record that points to itself is a root, and the root names the group.

  • find(i): follow parents until you reach the root.
  • union(i, j): point the root of i at the root of j, so the two groups become one.
  • Path halving: while walking up in find, point each node at its grandparent. Trees stay shallow, so later finds are fast.
General background

Union-find is a standard data structure. With path compression and union by rank, each operation is close to constant time. This code uses path halving only, which is plenty for a few hundred records.

The rule

edges E = { (i, j) : patient_i = patient_j  or  d(hash_i, hash_j) ≤ 12 }
groups = connected components of (records, E)
group_id(i) = patient_id of find(i)

Worked example

From test_patient_identity_links_near_duplicate_components: patients [a, a, b, c] with hashes [0, 2256−1, 1, 2256−2].

  • Records 0 and 1 share patient a: union.
  • Records 0 and 2: hashes 0 and 1 differ in 1 bit: union.
  • Records 1 and 3: all ones and all ones except the last bit differ in 1 bit: union.
  • Records 2 and 3 differ in all 256 bits, but they still end up in one group, through patient a.

Result: one group. On real Shenzhen data, there were 0 near-duplicate pairs and no shared patient IDs, so every record was its own group.

The code

Line by line

  • 171Start with every record as its own root: parent[i] = i.
  • 173-177find with path halving. Line 175 points i at its grandparent, then line 176 jumps there.
  • 181-186First pass: link every record to the first record seen with the same patient ID. Doing patients first means image links can join whole patients together but can never split a patient apart.
  • 188-191Second pass: every pair of records, with the Hamming distance from 3.7. That is n(n−1)/2 pairs: 190,653 for v2's 618 records.
  • 192-194Within the threshold: record the pair for near_duplicates.csv and union the two groups. Line 194 sets i's root to point at j's root.
  • 195Each record's group ID is the patient ID of its root, plus the list of pairs.

3.9 Reproducibility and provenance

The idea

Two months from now, someone will ask, "which data was this model trained on, and what code built it?" Reproducibility means you can rebuild the exact same dataset. Provenance means you can say where it came from.

"Random" splitting is still reproducible, because the code uses a pseudo-random number generator. It produces a sequence that looks random but is fully decided by its seed. Seed 591 always gives the same shuffle. The value 591 itself does not matter; what matters is that it is fixed and written down.

The run report records everything that could change the output:

  • the seed and the pipeline version;
  • Python, numpy, pandas and Pillow versions (a new Pillow can decode or resize slightly differently, which can change dHashes);
  • the git commit of the code, marked +dirty if the pipeline folder had uncommitted edits;
  • the dataset version hash from 3.6, which Team Rules 7 says to log with every training run.
General background

numpy's default_rng uses the PCG64 generator. A given seed gives the same stream on any machine running the same numpy version.

The rule

same raw bytes + same code + same library versions + same seed
⇒ same manifest and same dataset_version_hash

Worked example

The v2 run report: pipeline 0.2.1, seed 591, Python 3.10.12, numpy 2.2.6, pandas 2.3.3, Pillow 12.3.0, commit b21a47f... with no +dirty, hash 0445b087fed038c4. The synthetic README warns that PNG bytes can differ across machines, so each tester compares against their own baseline. On 10 Nov 2026 this machine reproduced the README's synthetic hash exactly.

The code

Line by line

  • 158The folder this file lives in, ml/pipeline/.
  • 160-161Ask git for the current commit.
  • 162-163git status --porcelain -- . run inside ml/pipeline/ lists uncommitted changes in that folder only. Any output means the code that ran is not exactly the commit.
  • 164-165No git, or not a repository: record "unknown" instead of crashing.
  • 166The commit, plus +dirty if needed.
  • 409-418The provenance fields at the top of run_report.json: what data, which version, which seed, when, and with what software and code.

3.10 Synthetic data and adversarial testing

The idea

The Shenzhen terms say "please do not share the dataset outside of your research group" (data card). But the course asks a paired team to attack your data path (ICS 591 Prosit 2, Section D). The answer is synthetic data: fake records with the same structure as the real ones (folders, file names, reading formats, including the messy ones) but none of the content. The images are random textures, not X-rays. They test the data path, not the model.

Adversarial testing means someone tries on purpose to break the system: flip a label, corrupt a file, plant a duplicate, edit a reading. They then check whether the outputs catch it. The method is: run once on clean data and record the hash (your baseline), attack, run again, and compare the manifest, the quarantine list and the report.

The generator decides each record with Bernoulli trials: a weighted coin flip. TB with probability 0.52, child with probability 0.04.

The rule

for i = 1..400:  label ~ Bernoulli(0.52)
              age ~ uniform 3..14 with probability 0.04, else uniform 15..80
expected TB = 400 × 0.52 = 208
expected children = 400 × 0.04 = 16,  standard deviation = √(400 × 0.04 × 0.96) ≈ 3.9

Worked example

Seed 2026, counted on 10 Nov 2026: 209 TB-labelled files (expected 208) and 19 children (expected 16, within one standard deviation). The clean run kept 381 and quarantined 19, all under 15, matching the README. Hash 1dd066baf6b0a52f. Near-duplicate pairs: 0, since independent random textures are far apart.

Documented history

The synthetic files share names with the real v1 manifest. Pipeline 0.2.0 and later carry splits from that manifest by default, which made the synthetic run fail its batch checks. The fix is to run with --keep-splits-from "" (testenv README, commit 3dcd816).

4. Where the code departs from the theory

Shortcuts the code takes, places where its behaviour differs from the textbook version, and places where a simpler method could have worked.

4.1 "Patient-level" is really image-level on Shenzhen

The theory groups by person. Shenzhen's patient_id is the provider's image sequence number (data card), and every kept record is its own group: 635 groups for 635 records in v1, and 618 for 618 in v2. If one person appears under two numbers with two different X-rays, neither the IDs nor the dHash can tell. The code can only group what the IDs and hashes reveal. The design is right; this dataset just cannot use all of it.

4.2 All-pairs comparison is quadratic

Both duplicate_label_conflicts and near_duplicate_groups compare every pair: 190,653 pairs each for v2's 618 records. That is fine at this size. For the 20,000-image retinal subset the TRD mentions (ML-DATA-06), it would be about 200 million pairs per pass. The run time was not measured.

General background

Standard fixes include a BK-tree, or splitting each 256-bit hash into 13 chunks. Two hashes within 12 bits must match exactly on at least one chunk (pigeonhole principle), so only records sharing a chunk need comparing.

4.3 A word list, not a negation detector

Clinical NLP has dedicated methods for spotting negation and uncertainty, such as NegEx (general background). The pipeline uses a short regex list instead. It is simpler and easy to audit, which suits a validation gate. The cost is real: it missed STB and dropped 16 probable TB records.

4.4 The 5-point gap is a fixed rule, not a statistical test

Because the split is stratified, the gaps are tiny (largest 0.010 in v2). Without stratification, a 93-record split would have a TB rate with standard deviation √(0.511 × 0.489 / 93) ≈ 0.052. It would miss the 5-point limit about a third of the time by chance alone (normal approximation, general statistics). So in practice the check catches bugs, like the giant chained group, rather than sampling noise.

4.5 Small details

  • Rounding. Python's round rounds an exact half to the even number. No exact half came up in v1's sizes, and the test split takes the remainder, so totals are always right. With very few groups for a label, the test split could be empty. Its TB rate would then be NaN, and the batch check would fail.
  • Age 0 as a code. Months and days become age 0, a number standing for "under one year." It works because 0 is under 15, but one field now holds two meanings.
  • Group label is the maximum. Stratification counts groups, not records, so a split's record-level TB rate can drift if groups are large. There was no effect on Shenzhen, where every group has one record.
  • An untested claim. The dhash docstring says it survives "small intensity changes." The tests check resizing only.
  • Median 72 vs 73. The README gives 73 as the median dHash distance. Recomputing over v1's 635 committed hashes gives 72. This is not a code issue, probably just a different set of images.

4.6 Where a library would have worked

General background, not used in this project: scikit-learn's StratifiedGroupKFold or GroupShuffleSplit do grouped, stratified splitting, and the imagehash package has a ready-made dHash. Neither carries splits over from an earlier version, so carry_splits would still be custom code. The pipeline needs only numpy, pandas and Pillow (ml/requirements.txt).
